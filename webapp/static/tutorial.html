1) Seguridad de acceso web

Ahora el dashboard exige autenticación básica en todas las rutas.

  • Prioridad 1: si defines TRADING_BOT_WEB_USER y TRADING_BOT_WEB_PASSWORD, usa esas credenciales.
  • Prioridad 2: si no hay variables, se crea config/web_auth.json con usuario/password aleatorios.
  • Recomendado para VPS: usar variables de entorno del sistema y restringir acceso de red (VPN o allowlist).

2) Flujo recomendado

Orden de trabajo para operar sin editar código.

1En /presets, revisa perfiles (SCALP/SWING) y presets.
2Crea asignaciones Canal.Preset (modo real o virtual).
3En / (Control), carga credenciales y arranca Lector y Operador.
4Monitorea en /operaciones, /reportes y /alertas.
5Audita mensajes en /mensajes por message_id o event_id.

3) Cómo decide cierres y modificaciones

Resolución de operación objetivo en el estado actual del bot.

  • Primero enlaza la señal por reply_to. Si no existe, usa message_id.
  • Luego busca en este orden: open_trades.csv -> operation_records (SQLite) -> orders_index.csv (fallback legacy).
  • La trazabilidad queda registrada con método de enlace, método de lookup y detalle del resultado.

3.1) Límite de modo real por canal

Regla de seguridad para evitar multiplicar operaciones reales por una misma señal.

  • Solo se permite 1 asignación real por canal.
  • El modo real solo se permite si el preset es perfil SWING.
  • Autogenerar cruce Canal x Preset reconstruye las asignaciones (borra y crea nuevamente el cruce completo).
  • Si intentas crear/editar una segunda asignación real para el mismo canal, la API devuelve error 409.
  • En /presets se muestra advertencia visual: “Máximo 1 asignación real por canal”.

3.2) Cierres por clase (SCALP/SWING)

Un cierre/modificación puede apuntar solo a SCALP o solo a SWING.

  • Si la señal dice cerrar SCALP, las posiciones SWING no se cierran.
  • Si la señal modifica SWING (por ejemplo mover SL a BE), los SCALP no se modifican.
  • Si la señal no especifica clase, se aplica a las operaciones abiertas relacionadas con ese mensaje.
  • En virtual, el cierre ignora close_pnl_pips reportado por señal y calcula pips por precio de mercado actual.

4) Protección ante falsos cierres por MT5

El Operador no cierra de inmediato si hay ausencia momentánea en MT5.

  • Si MT5 no responde (terminal_info/account_info), se salta sincronización de estado.
  • Una operación real se marca como “cierre manual detectado” solo tras múltiples chequeos consecutivos sin verla en MT5.
  • El umbral se controla con MANUAL_CLOSE_CONFIRM_CHECKS (default: 3).

5) Cola robusta de eventos

Manejo de eventos dañados para no bloquear operación 24/7.

  • Si un evento en queue/pending falla al procesarse, acumula retries en SQLite.
  • Al superar QUEUE_MAX_RETRIES (default: 5), se mueve a queue/failed (cuarentena).
  • Esto evita que un JSON corrupto frene reinicios programados o degrade todo el loop.

6) Reinicios 24/7 y persistencia segura

El reinicio automático y el botón de reinicio rápido usan la misma lógica de reinicio controlado.

  • El scheduler no reinicia si hay backlog en queue/pending; posterga y alerta.
  • La configuración de arranque de Lector/Operador se guarda cifrada en DB para sobrevivir reinicios de la webapp.
  • La clave de cifrado se guarda en config/runtime_env.key.
  • Si falta cryptography, el sistema usa fallback funcional no cifrado (recomendado instalar dependencias completas).

7) Lector y parser de señales

Procesamiento robusto para latencia/red inestable.

  • El parseo OpenAI se ejecuta en thread pool (no bloquea el loop de Telegram).
  • Hay timeout de parser: PARSER_TIMEOUT_SEC (default: 35).
  • Con timeout o excepción, el mensaje se guarda como no señal con motivo técnico.

8) Reportes y exportación

Estado actual de monitoreo y descarga de errores.

  • /reportes muestra curva por Canal.Preset, resumen y errores paginados.
  • Descargar Excel exporta la tabla filtrada de errores recientes.
  • La ruta legacy PDF redirige a Excel por compatibilidad.
